1. 프로젝트 개요
────────────────────────────────────────────────────────────────────────────────

목적:    신규상장(IPO) 종목 당일 LS증권 xingAPI로 HFT 스캘핑
환경:    AWS Lightsail Windows Server / 32-bit Python 3.10+ / xingAPI COM 32bit
메인:    hft_scalping_bot.py (~2100줄)
설정:    .env (인증·전략 파라미터) / config/ticker.json (종목)
실전서버: hts.ebestsec.co.kr:20001

파일 구조:
  hft_scalping_bot.py   메인 봇
  set_ticker.py         종목 설정 유틸 (python set_ticker.py 012345)
  .env                  인증정보·전략파라미터 (절대 깃 커밋 금지)
  .env.example          .env 템플릿
  config/ticker.json    매매 종목 (shcode, isu_no, start_time)
  logs/                 CSV 매매로그
  requirements.txt      의존성

실행 순서:
  python set_ticker.py 012345   # 전날 밤 종목 설정
  python hft_scalping_bot.py    # 당일 매매 (Ctrl+C 종료)

2. 전략 요약
────────────────────────────────────────────────────────────────────────────────

진입:  MA80 × (1 - ENTRY_GAP%) 지정가 1주 (BUY_PEGGED)
       기본 ENTRY_GAP=2%, STRATEGY_ENTRY_GAP_PCT 로 조절

가격추적 (PEG):
  - MA80 변동으로 호가단위가 바뀔 때만 정정/취소+재주문
  - 정정(CSPAT00700) 1회 허용 (AMEND_MAX_PER_ORDER=0 이면 처음부터 취소+재주문)
  - 2회째부터 취소(CSPAT00800) → 신규매수(CSPAT00600)

체결 후:
  - TP 지정가 매도 (TAKE_PROFIT=2%)
  - 4초 타임컷 → 익절 취소 → 시장가 매도

4. 아키텍처
────────────────────────────────────────────────────────────────────────────────

[메인 스레드]
  PumpWaitingMessages 루프
  XARealTickEvents.OnReceiveRealData  → tick_queue.put_nowait
  XARealOrderEvents.OnReceiveRealData → fill_queue / order_event_queue.put_nowait

[워커 스레드] (CoInitialize, 독립 XAQuery)
  처리 우선순위: SC1(체결) > SC0/SC2/SC3/SC4 > TR ACK > 틱
  MA 계산, 주문 발송, 타임컷, REPEG settle

[로그 스레드]
  log_queue → print + CSV 기록 (핫패스 완전 분리)

큐:
  tick_queue         K3 시세틱
  fill_queue         SC1 체결
  order_event_queue  SC0/SC2/SC3/SC4 주문이벤트
  order_ack_queue    CSPAT TR 응답·메시지
  log_queue          로그

6. 50ms 레이턴시 달성 가능성 분석
────────────────────────────────────────────────────────────────────────────────

【결론 먼저】
  - MA 계산 → 주문발송: 1ms 미만 (내부 처리)
  - 주문발송 → ACK: 30~80ms (LS 실전 서버, AWS 서울 EC2 기준)
  - 정정 1회: ~30~60ms (50ms 경계에 걸침)
  - 취소+재주문: ~80~150ms (50ms 불가)
  - 연속 PEG 추적(취소+재주문): 50ms 구조적으로 불가능

【병목 구간 분류】
  ① 봇 내부 (틱 큐→MA→주문발송): <1ms            ✅ 문제없음
  ② TR 왕복 (발송~ACK): 30~80ms                   △ 정정만 50ms 가능
  ③ 취소+재주문 (TR×2 직렬): 80~150ms             ❌ 50ms 불가
  ④ REPEG_SETTLE 400ms 대기: 설계상 400ms         ❌ 50ms 불가 (의도적)
  ⑤ IPO 초반 LS 서버 부하 지연: +50~200ms 추가    ❌ 가변적

【LS xingAPI 리테일 구조적 한계】
  - 거래소 코로케이션 아님 → TR 왕복 최소 30ms
  - COM 싱글 XAQuery 객체 → 동시 TR 1개 처리
  - 정정 2회째부터 02714 → 취소+재주문 강제
  - 취소 후 재주문까지 2 TR 왕복 최소 60ms+

【50ms 이내 가능한 것】
  - 첫 정정(CSPAT00700) 1회: 빠른 날 35~50ms 가능 (빠른 편)
  - SC1 수신→익절 지정가 발송: 내부처리 <1ms + TR 왕복 ~40ms
  - MA 계산 자체: <0.1ms

【50ms 이내 불가능한 것】
  - 정정 2회 이상 연속 PEG 추적
  - 취소+재주문 방식의 PEG 추적
  - IPO 초반(09:00~09:05) 서버 부하 시 모든 TR

【비교: 한투 REST API + 우분투】
  - TR 왕복 자체는 비슷 (30~80ms, 서버 위치가 핵심)
  - 우분투는 COM GIL 없어 다소 유리, 그러나 10배 빠르진 않음
  - 정정 횟수 제한: 증권사마다 다름 (한투는 여러 번 가능할 수 있음)
  - 차이가 난다면 정정 여러 번 허용 여부 (LS 2회 제한이 핵심 병목)

7. 현재 코드 구조 문제점 및 잠재 버그
────────────────────────────────────────────────────────────────────────────────

[ISSUE-01] 워커 루프 틱 처리 1개씩
  현재: tick_queue.get(timeout=0.001) → 1개 처리 후 다시 상단으로
  문제: 300~500틱/초 버스트 시 tick_queue 누적 → MA가 오래된 값 기준
  개선안: _drain_queue(tick_queue, engine.process_tick) 으로 한 번에 비우기
  주의: 변경 시 한 루프에서 MA 300회 계산 → CPU 부하 확인 필요

[ISSUE-02] REPEG_SETTLE 중 queued_buy_limit 갱신 누락
  현재: settle 중 틱이 와도 _can_sync_pegged_price() False → queued_buy_limit 갱신 ok
        그런데 settle 해제 직후 _poll_repeg_settle이 queued 값 사용 → 정상
  상태: 현재 설계상 ok, 단 settle 길면 MA 많이 이탈 후 오래된 가격으로 재주문 위험

[ISSUE-03] 취소+재주문 도중 SC1(체결) 레이스
  시나리오: 취소 TR 발송 후 ~ SC3(취소확인) 전에 SC1(체결) 도착
  현재 처리: buy_cancel_in_flight=True이면 _handle_buy_fill에서 RECOVER 경로
  위험: in_replace=True 상태에서 체결 → _repost_pegged_buy 실행 안 함 → 정상
        CANCEL+FILL 레이스 시 매도 주문 발송 잘 되는지 확인 필요 (로그 검토 권고)

[ISSUE-04] 매수 ACK에서 buy_settle_until 덮어쓰기
  현재: REPEG 매수 ACK 시 _mark_buy_settle() 호출
        최초 매수(PEG)도 ACK 시 동일하게 settle 적용됨
  영향: 최초 매수 후에도 400ms 동안 정정/취소 금지
        → 빠른 가격 변동 시 첫 정정 타이밍 늦어짐
  개선안: REPEG 재배치 시에만 settle 적용, 최초 PEG는 settle 없애기

[ISSUE-05] _flush_queued_amend 루프 위험
  현재: flush 후 조건 불만족 시 queued_buy_limit = target 복구
        → 다음 틱에서 다시 flush → 정상이면 ok
  위험: _can_sync_pegged_price() 계속 False일 때 매 틱마다 flush 시도
        (실제 TR 미발송이라 문제는 없으나 로그 없어서 추적 어려움)

[ISSUE-06] BUY_ORDERED 상태 하위호환 처리 미흡
  현재: BotState.BUY_ORDERED alias만 정의, 실제 전환 로직 없음
  영향: 이전 세션 코드와 호환만 유지, 실전 사용 안 함
  권고: 다음 정리 시 제거

[ISSUE-07] set_ticker.py isu_no 자동 설정 없음

  문제: 신규상장 종목 일부는 isu_no 형식이 다를 수 있음 (예: Q+shcode)

[ISSUE-08] 멀티 XAQuery 없음
